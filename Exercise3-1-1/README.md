# Exercise 3-1-1 Reflection

## 1. Rule Ownership
Assign each validation rule to Program.cs, Student, or StudentParticipation. Explain why each owner has the state, knowledge, and authority needed to enforce the rule.
###### Student.cs: Validation for first name, last name, student ID, and email belong to the Student class because, following the logic and rules of the scenario, they determine whether or not a given Student object is in a valid state. Student has the knowledge to enforce these rules because the class is used to represent a Student. The class has the state to enforce these rules because it owns them and protects the data the rules apply to. Finally, the class has the authority to enforce these rules because it should internally control its modifications. 
###### StudentParticipation.cs: Validation for action choice, action name, maximum points, and points earned belong to the StudentParticipation class because these values determine whether a StudentParticipation object is in a valid state. StudentParticipation has the knowledge to enforce these rules because it defines the relationship between each participation action and its maximum point value. The class has the state needed to enforce the rules because it stores student info, action name, maximum points, and the total points earned. Finally, the class has the authority to enforce these rules because it controls the construction of the participation record and all changes to points earned through UpdatePoints method.
###### Program.cs: Program.cs is responsible for collecting input, creating domain objects, calling their public methods, and displaying results. It has the state needed for this responsibility because it temporarily stores the values entered by the user. It has the knowledge needed to prompt the user and pass those values to the appropriate objects. The Program class's authority is limited to requesting construction or state changes. Program.cs should not enforce Student or StudentParticipation domain rules because the domain classes have the knowledge, state, and authority needed to determine whether their own objects are valid.
## 2. Student Invariants
State at least four class invariants for Student. Phrase each as a condition that is true for every successfully constructed Student.
###### Four class invariants for the Student class include first name, last name, student ID, and the student's email. The first name must not be null, empty, or contain whitespaces. The same conditions are true for the student's last name. Student ID must be nine digits long, start with "800", and only contain numeric characters. Email must end with "@charlotte.edu".
## 3. StudentParticipation Invariants
State at least four class invariants for StudentParticipation. Include the relationship among ActionName, MaximumPoints, and PointsEarned.
###### Four class invariants for the StudentParticipation class include the student info, action name, maximum points, and points earned. The relationship between action name and maximum points is that each action has a maximum points value assigned to it, as per the scenario. Maximum points governs points earned in the fact that points earned must be less than maximum points. Maximum points acts as a relationship bridge between action name and points earned.

## 6. Public-Interface Audit
Explain how a public PointsEarned setter could bypass the domain rules. State whether your final public interface contains this design gap.
###### A public points earned setter would bypass domain rules because it would allow the program class to explicitly change the value of points earned, while also bypassing the validation methods imbedded in the StudentParticipation class. Points earned has a private scenario regarding this instance of the StudentParticipation class, so it does not contain this design gap.
